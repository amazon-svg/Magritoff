# T03.WM3 — Plugin Magento — enrichissement CMS sans remplacement

> Permet à un imprimeur équipé de Magento d'ajouter les produits Magrit à son catalogue existant, sans toucher à ce qui y est déjà.

## Valeur métier

Les clients sous Magento sont des gros comptes : leur catalogue représente des années de travail, de référencement et d'intégrations annexes. Leur proposer de remplacer tout cela, c'est leur proposer un projet de migration, pas un outil — et c'est perdre la vente. La stratégie d'enrichissement retourne l'argument : Magrit s'ajoute, ne remplace rien, et le coût d'adoption tombe à l'installation d'un module. Le vrai critère de réussite n'est pas que les produits Magrit apparaissent, c'est que le catalogue Magento existant soit intact après l'opération. C'est ce que vérifiera le client avant toute autre chose.

## Besoin utilisateur

_Non formulé dans la source Notion._ La description désigne l'imprimeur équipé de Magento comme bénéficiaire, mais le besoin n'est pas écrit et n'est pas déduit ici. Il reste à formuler par l'autorité produit.

## Comportement attendu

1. Un module Magrit s'installe sur une instance Magento existante.
2. Une fois installé, les produits Magrit sont publiés dans le catalogue Magento, en s'ajoutant à ce qui s'y trouve déjà.
3. Un produit Magrit est associé à une fiche produit Magento, de façon durable.
4. Un panier constitué dans Magrit peut être transféré vers Magento.
5. Le catalogue Magento préexistant n'est ni modifié, ni supprimé, ni déplacé par l'installation ou par la publication.

## Expérience utilisateur

- La surface est l'administration Magento du client, pas celle de Magrit : le module doit s'y comporter comme un module Magento ordinaire, dans ses conventions.
- L'administrateur Magento doit pouvoir distinguer d'un coup d'œil les produits venus de Magrit de ses produits historiques, sans quoi il ne saura pas où intervenir en cas de problème.
- **La source est muette** sur : l'interface d'administration du module côté Magento, la configuration de la liaison, ce que voit l'acheteur lors du transfert de panier, les versions de Magento visées.

## Règles métier

- `RM-01` — Le module s'installe sur une instance Magento existante sans remplacement du catalogue en place. L'approche est l'enrichissement, retenue pour réduire le coût de migration du client.
- `RM-02` — Un produit Magrit est associé à une fiche produit Magento ; l'association est durable et permet la mise à jour.
- `RM-03` — Un panier constitué dans Magrit peut être transféré vers Magento.
- `RM-04` — Le périmètre de validation de cette story est une instance Magento de test, non une mise en production chez un client.
- `RM-05` — L'architecture mise en place pour PrestaShop (`T03.WM1`) est réutilisée ; cette story ne crée pas un second modèle d'intégration.

## Critères d'acceptation

- `AC-01` — Étant donné une instance Magento de test portant un catalogue existant, quand le module Magrit est installé, alors l'installation se termine sans erreur et le catalogue préexistant est inchangé.
- `AC-02` — Étant donné le module installé, quand 3 produits Magrit sont synchronisés, alors ces 3 produits apparaissent dans le catalogue Magento, en plus des produits préexistants.
- `AC-03` — Étant donné un produit Magrit publié, quand on consulte l'association, alors le produit Magrit et la fiche Magento sont reliés de façon identifiable des deux côtés.
- `AC-04` — Étant donné un produit Magrit déjà publié, quand il est modifié puis republié, alors la fiche Magento existante est mise à jour et aucune fiche en double n'est créée.
- `AC-05` — Étant donné un panier constitué dans Magrit, quand le transfert est déclenché, alors le panier Magento contient les mêmes lignes, dans les mêmes quantités.
- `AC-06` — Étant donné le module désinstallé, quand on inspecte l'instance Magento, alors le catalogue préexistant est intact (**la source ne spécifie pas le sort des produits Magrit publiés après désinstallation**).

## Cas limites

- **Rien n'existe dans le dépôt** : aucun module Magento, aucune publication vers Magento. Le travail est entier.
- **Collision de référence.** Un produit Magrit et un produit Magento préexistant partageant la même référence ou la même unité de gestion de stock : la source ne dit pas lequel l'emporte, ni si la collision est signalée.
- **Désinstallation.** La source ne dit pas ce que deviennent les produits publiés quand le module est retiré, alors que c'est la première question que posera un gros compte avant d'installer quoi que ce soit.
- **Versions de Magento.** Magento 2 connaît plusieurs versions majeures et deux éditions. La source ne cible rien. L'estimation d'effort n'a pas de sens tant que le périmètre de versions n'est pas fixé.
- **Chevauchement avec `T03.1`.** `T03.1` liste Magento parmi les quatre plateformes à connecter par clé d'API, en sens entrant. Cette story livre un module installé côté Magento, en sens sortant. Ce ne sont pas les mêmes mécanismes ; les deux stories ne sont pas articulées.
- **Transfert de panier et identité de l'acheteur.** Même angle mort que dans `T03.WM1` : rien n'est dit sur la session et l'identité de l'acheteur entre les deux applications.

## Hors périmètre

- Toute remontée d'information de Magento vers Magrit.
- La mise en production chez un client : `RM-04` borne la validation à une instance de test.
- PrestaShop (`T03.WM1`) et Shopify (`T03.WM2`).
- La publication du module sur la place de marché Magento, non évoquée par la source.

## Dépendances et décisions

- `T03.WM1` — l'architecture de publication vers un CMS est mise en place pour PrestaShop puis réutilisée ici (dépendance déclarée en frontmatter, nommée par la source).
- `T03.WM2` — la source la cite comme « indépendante mais même logique d'intégration ». Ce n'est pas une dépendance : elle **n'est pas** reportée en frontmatter, l'étude Shopify ne conditionnant pas Magento.
- `T03.1` — liste Magento parmi les plateformes à connecter, en sens entrant. L'articulation entre les deux stories n'est pas tranchée.
- `ADR-2026-10-01-C1` — l'architecture cible n'utilise plus de fonctions Edge : l'endroit où s'exécute la publication reste à définir. Les éléments de mise en œuvre serveur hérités de l'import ont été retirés.
- Donnée de contexte issue du cadrage WM du 12/05/2026 : la stratégie d'enrichissement, et non de remplacement, est retenue pour réduire le coût de migration (transcription Doc4 01:35:02).
